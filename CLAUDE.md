Guidance for Claude Code working in the **passwordepic-website** repository.

## What this repo is

The public site for `passwordepic.com` — the marketing page, the legal pages
Google Play requires, and a growing user guide. Docusaurus 3, TypeScript config,
deployed to GitHub Pages by `.github/workflows/deploy.yml` on every push to
`main`.

It is **not** the app. The app lives in a separate repository — see below.

```
src/pages/index.tsx     landing page (React)
src/pages/privacy.md    /privacy  ← Google Play fetches this URL
src/pages/terms.md      /terms
src/pages/support.md    /support
docs/                   user guide, autogenerated sidebar
static/img/             images; static/ is copied to the site root
static/CNAME            custom domain for GitHub Pages
```

```
npm install
npm start        # local dev at :3000
npm run build    # must pass before pushing — the workflow runs the same build
```

## Four claims that are false

These read naturally, sound like ordinary marketing, and are wrong. Each has
already appeared in this project's own documentation at some point.

1. **"AES-256-GCM"** — true for Gold, Platinum and Titanium only. Silver is
   `crypto-js` AES-256-CTR with a separate HMAC-SHA256, in JavaScript, with no
   hardware key storage. Never describe the free tier as GCM or hardware-backed.
2. **"Move your vault to a new phone" / "cross-device restore"** — does not
   exist on any tier. Export and backup files carry a StrongBox/TEE layer and
   open only on the device that wrote them. Losing the phone loses the vault.
3. **"Blocks screen recording"** — `FLAG_SECURE` blacks out the app's own
   windows but never the keyboard, and refusing passcode entry while a recording
   runs is Android 15+ only.
4. **"Available on iOS"** — there is no iOS build. No App Store badge, no Apple
   logo, no Face ID or Touch ID in feature lists.

Safe to say: **zero-knowledge** (accurate), and **one device per account** for
paid tiers — but frame that as seat licensing and safety, not as what protects
the passwords. Shard1 never leaving the device is what does that.

## Say the limitation out loud

The front page states that there is no account recovery and no device migration.
That is deliberate and should not be softened into "contact us for help" or
buried in the FAQ.

For a password manager, "we cannot recover your vault" is the *evidence* that
the key is genuinely beyond our reach — it is the product's strongest claim, not
its weakest. And a user who discovers it after losing a phone has lost
everything while believing otherwise.

## Two things that must not break

- **`/privacy` must resolve.** Google Play fetches it when reviewing the
  listing, and the app links to `https://passwordepic.com/privacy` from
  `src/constants/contact.ts`. Do not rename or move that route.
- **`support@passwordepic.com` must reach a human.** For a user whose bound
  device is lost, emailing support is the *only* way back — `releaseDevice`
  requires that device's StrongBox signature, so support editing Firestore is
  all that remains.

## Adding content

Images go in `static/img/` and are referenced as `/img/name.png`. Prefer a
hosted player for video over committing large files. `onBrokenLinks: 'throw'` is
set on purpose: a dead link to the page that qualifies a claim is how the
unqualified version survives, so the build fails instead.

Run `npm run build` before pushing. The deploy workflow runs the same command,
so a build that fails locally fails in CI too.
